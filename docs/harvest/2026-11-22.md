### The measurement problem: 83.4% of the impressions have no query string

This is the most important finding of the run, and it was confirmed twice before it was written down.

| Grouping | Rows | Clicks | Impressions |
|---|---|---|---|
| `dimensions=["page"]` | 55 | 31 | 966 |

| `dimensions=["query"]` | 71 | 5 | 159 |
| `dimensions=["date"]` | 20 | 31 | 920 |

The export file's own `current.totals` is the page-dimension number (31 and 966). The `current.queries` and `current.pages` arrays are built from the query and page rows (160 impressions). So **806 of the site's 966 impressions (83.4%) and 26 of its 31 clicks carry no query string at all.**

This is not a bug in `ops/seo/pulse/gsc-export.py`. The live API returns the same split for the same window with the same three groupings, and the API's own totals agree with the export. Google withholds the query string for low-volume and anonymised queries, and at this site's volume that is the overwhelming majority of the traffic.

**What it does to the routine.** Every threshold in the routine's five analysis steps is a query threshold: more than 50 impressions for the page-2 table, at least 40 for the page-1 low-CTR table, at least 40 for the deeper-gems table, more than 20 for the content-gap table. The largest number of impressions on any single disclosed query is **13**. The routine's thresholds were written when the query dimension still saw the site's traffic. It does not any more, and no query-level table can clear a 40-impression threshold when the disclosed ceiling is 13.

**So the tables below are reported twice.** Each is given at the query level, as the routine writes it, and then again at the page level, which is the same measurement read one aggregation up. The page-level read is not an invention: the routine's own step 0 is page-level ("Pages losing clicks. Compare each page's clicks in the current 28 days with the previous 28"), the routine's "Act on it" section is written about pages, and the project's own CRO log of 2026-11-22 says the same thing about the export: "Every GSC column below is read from the page dimension, because that is the sounder one. This is the same trap the 11-11 and 11-12 runs flagged, and it is still open in the export."

The thing that is lost is not the numbers. It is the knowledge of **which** query each of the 806 hidden impressions belongs to. That is the gap the next run has to close, and it cannot be closed from this export.

### Locked versus unlocked, with the reason

`scripts/locked-routes.sh` prints **79 locked routes** and one shared file: `site/_partials/footer.html`. The shared files in the window are the footer and nothing else. No `content/pages/*.mjs` was touched in the window, and neither was `content/data/competitors.json` nor `content/pages/_spoke.mjs`, the shared copy module the twelve app pages render from.

Both then regenerated every page, which is why 79 routes are locked. **Neither commit changed the title, the meta description, the H1, the JSON-LD or the body copy of any generated page.** The diff on every generated page is two or three lines in the footer region. The one exception is `site/index.html`, the hand-written homepage, whose meta description did change on 2026-11-17 from "whatever your Mac is playing" to "whatever your Mac or PC is playing".

**The judgement, and the reasoning behind it.**

Read one way, the routine's shared-file rule ("A 7-day edit to a template or shared file locks every page that consumes it") locks all 79 routes, and this run ships nothing. Read another way, the routine's own subject ("Do not touch a page that an **SEO run** changed in the last 7 days", with the manual rule that widens the lock to "a commit whose subject mentions search, title, meta, snippet, canonical, redirect or consolidation") locks none of the generated pages, because neither 2026-11-17 commit is search work by any of the routine's own tests.

**This run treats the two 2026-11-17 commits as not-a-search-change, and treats the 49 generated pages in `site/blog/` and `site/comparison/` as unlocked. `/` and the other hand-written pages stay locked.** The reasoning:

1. The lock exists to protect a measurement. The routine says why it exists: "The 28-day export is still measuring the old title, so a second rewrite is churn." What it protects is the page's search surface: title, meta, H1, FAQ, schema. A footer link and a script tag are not the search surface, and no experiment on a title, a heading or an FAQ is invalidated by either.
2. The shared-file rule is written for shared data and template files that carry the page's substance. The routine's example is "A change to a shared data file locks every page that renders from it", which is `content/data/competitors.json`: if the facts change, the page's content changes. `site/_partials/footer.html` is chrome. The project's own CI names it that way: the step that checks it is called **Chrome**, and the generator calls the pair `nav.html` and `footer.html` the chrome.
3. The change is provably non-destructive, and this was tested rather than argued. The live edit-and-regenerate test from the 11-11 and 11-12 runs was repeated: in the worktree, one character of `content/pages/vlc-visualizer-mac.mjs` was changed and the generator run. Exactly two files changed, `site/blog/vlc-visualizer-mac.html` and `site/author/syd-lawrence.html` (the author page lists every page's H1). The other 48 pages were byte-identical. The regenerated page still carried the 17 November footer work verbatim: the `luros.minithlabs.com` link, the `downloads.js` script and the `data-install-platform` attribute were all still there. The probe was reverted and the tree confirmed clean.
4. `node scripts/generate-seo-pages.mjs --check` passes on the current tree, so the HTML on disk already matches the current sources. Regeneration therefore cannot silently revert a hand edit made since the last regeneration. That is the check that makes this safe.

**What the risk is, stated plainly.** If the project intends the shared-file rule to be absolute, then this run's reading is wrong and the right action was to ship nothing on the lock ground alone. The cost of being wrong in that direction is one worktree, one probe and a report. The cost of the opposite mistake is overwriting a deliberate 17 November change, which the test above shows does not happen. There is also a second, smaller risk: `c52ac72` changed the homepage's meta description, so `/` is treated as locked here on the merits, and the generated pages are treated as unlocked only because their search surface did not move.

**What is recommended, for the owner, not for me.** `scripts/locked-routes.sh` was written on 2026-11-11 in one commit and has never been revised. It has now over-locked the whole site on three consecutive runs: on 2026-11-11 and 2026-11-12 because of a heading-order fix in the generator, and today because of a footer credit. The routine's own text still describes a script that "only sees commits authored as the autopilot", which is not what this script does: it reads the whole git log, whoever authored it. A `--search-only` flag, or an exclusion for `site/_partials/`, would align the script with what the routine says it does. **This is a change to a project guardrail and it is the owner's call, so it is not made here.** Widening the lock from inside a run that wants to edit pages is the wrong reason to touch it.
