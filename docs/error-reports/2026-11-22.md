### 1.1 The traffic in this project is not classified as human traffic

This is the run's real finding in the product, and it was not in any of
the lists. It came out of the bot check, which flagged every event.

PostHog sorts the traffic it stores into human and not-human by reading the
user agent on each event. An event that carries none is classified as
automation: traffic type `Automation`, category `no_user_agent`, and
`isLikelyBot` is true for it.

The project's own classification, read back out of the project:

| Event | Count, last 30 days | Traffic type | Category | `$virt_is_bot` |
|---|---|---|---|---|
| `$pageview` (the site) | 1,565 | Automation | no_user_agent | true |
| `genre_detected` (the app) | 3,818 | Automation | no_user_agent | true |
| `mode_card_viewed` | 486 | Automation | no_user_agent | true |
| `download_clicked` (the site) | 43 | Automation | no_user_agent | true |
| `download_requested` (the Worker) | 883 | Automation | no_user_agent | true |
| `checkout_started` (the app) | 1 | Automation | no_user_agent | true |
| `Application Opened` (PostHog iOS SDK) | 1,137 | **Regular** | **regular** | **false** |
| `Application Installed` (PostHog iOS SDK) | 28 | Regular | regular | false |
| `$identify` (PostHog iOS SDK) | 28 | Regular | regular | false |

The last three rows are the same app, reporting through the PostHog SDK
instead of the project's own client. A mobile SDK is exempt from the
empty-user-agent rule, so those are the only events in the project PostHog
reads as a person.

Nothing errors. The events are stored, the counts are right, and the traffic
is filed under the wrong heading, so it drops out of every PostHog view
filtered to human traffic — the filter PostHog's own documentation gives for
measuring people.

The property that counts was measured rather than assumed. Four events were
posted to the project, one per case, and the classification was read back:

| Properties sent | Traffic type | Category | `$virt_is_bot` |
|---|---|---|---|
| `$raw_user_agent` | **Regular** | **regular** | **false** |
| `$user_agent` | Automation | no_user_agent | true |
| both | Regular | regular | false |
| neither | Automation | no_user_agent | true |

`$raw_user_agent` is the property the classifier reads. `$user_agent` on its
own is read by some PostHog functions and ignored by the classifier, so a
client that sends only that is still automation traffic.

The site is serving the code that has this defect right now:
`curl https://vibresia.com/analytics.js` is byte-identical to
`site/analytics.js` at `origin/main`, and it contains `$session_id` and no
`$raw_user_agent`.

**Shipped as a fix — see section 8.**

### 7.1 `download_requested` shows one person for 883 downloads

The server-side download counter reports 883 events over 30 days and exactly
**one** unique person. That looks like a broken visitor id, and it is
deliberate: `worker/index.js` sends `distinct_id: "downloads"`, and the
comment above it says why.

> The distinct id is a constant, and that is a decision rather than an
> oversight. The site knows which visitor downloaded, but the Worker does not:
> the browser's id is in its local storage, and putting it in a download link
> would hand it to every service that fetched the link.

The privacy reasoning holds, so the event carries no `$session_id`, no
`$current_url` and no `$browser`, by design. The person-level signal is the
site's own `download_clicked`, and it works: 43 clicks from 37 people over
30 days. The `source` field names where the link was placed, and the
placements are all real: `hero` (33 in 7 days), `hero-windows` (19),
`hero-mac` (15), `footer` (15), `after_gallery` (14), the `install-choose-*`
and `install-*` choosers, `ai-install-windows`, `share_fallback`, and the
`seo-*` search pages.

**This is the one that the fix in section 1.1 changes.** The count is the
number the project is judged on, and it was filed as automation traffic, so
it would read as zero in every view filtered to human traffic.
