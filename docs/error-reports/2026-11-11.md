### Why both were resolved rather than fixed

Both issues carry the same exception type, `PostHogLocalTestError`, and the
description is a Foundation error string whose module prefix is `AudioVane`,
the app's module name.

The evidence that these are deliberate local test errors and not a product
defect:

- The exception type is literally named `PostHogLocalTestError`. It is not
  a name any Vibresia code could produce: a search of the whole app source,
  the whole git history, and the pinned PostHog iOS SDK 3.92.0 source finds
  no such type anywhere. It was defined outside the repository, in a local
  harness that was never committed.
- The two events happened 4 seconds apart, in one session, from a local
  build of version 0.10.214, which was never a release. The window around
  them shows the app launching, throwing, and being backgrounded.
- These are the only two `$exception` events in the entire project
  history. Nothing has thrown since 21 October.
- The app version they came from has been superseded by fifteen releases.

Both were PATCHed to `resolved` during this run, not deferred. The issue
list was re-read afterwards and reports zero active issues.

## 6. Health and volumes

Five health issues are active. One was fixed in this run. The other four
are configuration or coverage gaps, and three of them describe the same
underlying defect.

### 6.1 `sdk_outdated` (critical), fixed

PostHog flagged the pinned PostHog iOS SDK as out of date: "Latest in-use
version 3.92.0 is behind 3.94.3 (32 days old)". The app was on 3.92.0.

Moved to 3.94.3 in PR #41. The change between the two versions that matters
here is in 3.94.1: a crash report written before an opt-out is no longer
sent after analytics is turned back on. That is this app's opt-out path
(`Analytics.setEnabled`). The 3.94.0 change that stops swizzling
`layoutSublayers` does not apply, because the app has no session replay and
no surveys.

`swift build` and `swift test` pass against the new version.

### 6.2 `missing_session_id` (warning), fixed

PostHog said 100% of `$pageview` events (543 of 543) carried a `$session_id`
web analytics could not use. Measured directly, before the fix:

- 548 of 548 `$pageview` events had no `$session_id` key in the properties
  bag at all. It was absent, not present-and-null.
- `uniq(properties.$session_id)` over the same window = 0.
- The raw event from `GET /api/projects/673583/events/?event=$pageview`
  confirms it: the event's own keys are `id`, `distinct_id`, `properties`,
  `event`, `timestamp`, `person`, `elements` and `elements_chain`. There is no
  top-level `session_id` on the stored event, and `properties` holds
  `$current_url`, `$referrer`, `path`, `title` and the geo fields, but no
  `$session_id` and no `$window_id`.

Two things were wrong, and fixing only the first would have changed
nothing.

The site sent its session id as a top-level `session_id` key on the event
object. PostHog reads `$session_id` from the properties bag, so a
top-level key is not a property and never arrives. The Worker forwards the
payload verbatim (`worker/index.js`, `handleIngest`), so the fix belongs in
the site.

The id was also a UUIDv4 from `crypto.randomUUID()`. PostHog counts an
event towards a session only when the session id is a UUIDv7, and states
that events which do not meet this are not included in session
aggregations.

`site/analytics.js` now builds a UUIDv7 itself and puts it in the
properties bag. One subtlety is worth recording: the timestamp is written
as 16 bits of high word and 32 of low. Writing the high half as a full
32-bit word puts the timestamp four bytes along, and the result still looks
like a well-formed v7 while decoding to a date in the year 7607. A test
decodes the id and checks it against the clock, because nothing else would
have noticed.

### 6.3 `no_pageleave_events` (warning), not fixed

PostHog says: "Team has $pageview events but no $pageleave events in last
30 days". The site sends `$pageview` by hand and never sends `$pageleave`.

This is left open deliberately. Sending `$pageleave` by hand would make
the site report a page leave it never observed: the page is a static HTML
file with no router, so there is no navigation for a pageleave to
describe. The honest fix is PostHog's own web vitals and pageleave
capture, which needs the official snippet, and that snippet pulls in
session replay, surveys, feature flags and a cookie banner. The site's
analytics client is deliberately minimal and says so at the top of the
file. Adding the snippet to satisfy a health check would be a product
decision, not a fix.

### 6.4 `web_vitals` (warning), not fixed

PostHog says: "Team has $pageview events but no $web_vitals events in last
30 days". Web vitals need the official snippet's capture, for the same
reason as 6.3.

### 6.5 `reverse_proxy` (warning), not fixed

PostHog says: "No reverse proxy detected. Ad blockers may affect tracking
accuracy." This is a configuration choice, not a bug. The site already
proxies through the Worker's `/ingest` route rather than sending to
PostHog directly, so a blocklist naming PostHog's host does not drop the
visit. Adding a second proxy layer is a decision for the owner, and
PostHog's own guidance on ad blockers is that around a third of visitors
use one.
