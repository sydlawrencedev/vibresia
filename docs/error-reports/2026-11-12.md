### 1.1 The `concat` rule, and where it stops

The routine's §0a says every event filter must be written
`event = concat('$', '<name>')`, because HogQL parses `$name` inside a string
literal as a field reference and the comparison form is rejected. That is
right, and it is right **for event names that begin with a `$`**.

It is wrong for this project's own events, and it fails in the same quiet way
the rule warns about. `concat('$','download_requested')` builds the string
`$download_requested` — with a dollar sign the event does not have — and
matches nothing. Measured side by side in the same run:

| Filter | Rows |
|---|---|
| `event = concat('$','download_requested')` | 0 |
| `event = 'download_requested'` | 235 |

The same applies to `download_clicked`, `install_command_copied`,
`share_opened`, `share_link_copied`, `share_pill_clicked`, `app_launched`,
`app_crashed`, `genre_detected`, `demo_played`, `session_summary`,
`custom_vibescape_failed`, `share_import_failed` and `share_video_failed` —
every custom event this project sends, all of which are named without a `$`.

The rule to use instead: **`concat` for `$`-prefixed names, a plain literal
for everything else.** The tell is in the name. `'$pageview'`,
`'$exception'`, `'$rageclick'` and `'$recording_observed'` need `concat`;
`download_requested` and everything else this project sends does not.

This cost real time in this run and nearly put a wrong number in the report:
a verification query using `concat` returned zero rows and looked like a
legitimate result, and the correct numbers only appeared once the filter was
written as a literal. The numbers in this report were re-checked with the
correct form.

### 7.1 `download_requested` shows one person for 235 downloads

The server-side download counter reports 235 events over 7 days and exactly
**one** unique person. That looks like a broken visitor id, and it is worth
saying why it is not.

`worker/index.js:429` sends `distinct_id: "downloads"` — a constant. The
comment above it, at lines 418 to 422, states the decision plainly:

> The distinct id is a constant, and that is a decision rather than an
> oversight. The site knows which visitor downloaded, but the Worker does not:
> the browser's id is in its local storage, and putting it in a download link
> would hand it to every service that fetched the link. So this event counts
> downloads, and the count of people comes from the site.

The privacy reasoning holds: the Worker serves a public download URL, and
stuffing a visitor id into that URL would leak it to every link preview and
scanner that fetched it. So this event carries no `$session_id`, no
`$current_url` and no `$browser`, by design.
