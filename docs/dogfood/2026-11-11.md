# Dogfood testing: Vibresia, 2026-11-11

**Target: production.** `https://vibresia.com`, the live deployed site.

**Verdict: one real issue found and fixed. The rest of the site is clean.**

---

## 1. What was tested and how

### The target

The routine's default target is `http://localhost:3000`. There is no Next.js dev
server in this project: it is a static site in `site/`, a Cloudflare Worker in
`worker/index.js`, and a macOS app. The Worker serves the site.

`npx wrangler dev` was **not** used, for two reasons:

- `wrangler` is not installed in this repository (`npm ls wrangler` is empty, and
  there is no `wrangler` in `node_modules/.bin`), so there was no local Worker
  runner to start without adding a dependency.
- The live site is the better target anyway. A local Miniflare instance would
  exercise the Worker in isolation, but not Cloudflare's edge: the caching, the
  `Speculation-Rules` header, the redirects and the real TLS path all live in
  front of the Worker. Production is where a visitor actually is.

**Everything below was tested against production at `https://vibresia.com`.**

### Browser

`agent-browser` is not installed on this machine. Google Chrome is, and Playwright
1.65.0 is available (`npx --no-install playwright --version`), with Chromium
build 1254 already in the Playwright cache.

The driver scripts live outside the repository, in
`/private/var/folders/56/5lf7zsws0pqbzmj3fnv0gwnc0000gn/T/opencode/dogfood/`.
Nothing was written into the working tree except this report.

### The pages

Every page in every sitemap, driven in a real browser at 1440x900:

### The methods

| What | How |
|---|---|
| HTTP status of every page | Playwright `goto` with `networkidle` |
| Console errors | `page.on('console')` for `error` and `warning`, plus `page.on('pageerror')` |

| 4xx and 5xx responses | `page.on('response')`, status >= 400 |

| Mobile | 390x844 viewport with `isMobile` and `hasTouch`, checking for horizontal overflow and footer navigation |
| Project checks | `npm test`, `node scripts/check-links.mjs`, `node scripts/generate-seo-pages.mjs --check`, `node scripts/check-schema.mjs` |

## 2. Issues found

### ISSUE-001: The heading order skips a level on nine pages

**Severity: medium.** It affects anybody navigating the site by heading, which
is the primary way a screen reader user moves around a page of prose. It is not
a crash, and it does not affect the visual design at all.

#### What it is

The "Pick X if" verdict box is the first thing under the `H1` on every
comparison page, and its headings were `H3`:

```html
<h1>Vibresia vs TouchDesigner: the simpler alternative for ...</h1>
...
<h3>Pick Vibresia if</h3>
<h3>Pick TouchDesigner if</h3>
<h2>Why Vibresia is the better pick for music visuals</h2>
```

The outline opens `H1` then `H3`, so `H2` is skipped. A screen reader reading by
heading sees the page begin part-way down, with the section it expected
missing.

`/agents` had the same jump. Its `H1` is followed by a lead-in paragraph and
then a boxed panel whose heading was `H3`:

```html
<h1>Let your agent<br><span>build the visuals.</span></h1>
<p class="lede">Vibresia comes with a small local server that AI assistants can talk to. ...</p>
<div class="setup">
  <h3>Or use the web version</h3>
```

#### Which pages

Eight of the thirty-five comparison pages, plus `/agents`:

```
/agents
/comparison/nestdrop-vs-milkdrop
/comparison/projectm-vs-milkdrop
/comparison/vibresia-vs-magic-music-visuals
/comparison/vibresia-vs-plane9
/comparison/vibresia-vs-projectm
/comparison/vibresia-vs-shadertoy
/comparison/vibresia-vs-synesthesia
/comparison/vibresia-vs-touchdesigner
```

The other twenty-seven comparison pages are fine: their first `H2` is the
"Control and connections" table, which precedes the verdict box.

#### Reproduction

1. Open `https://vibresia.com/comparison/vibresia-vs-touchdesigner`
2. In DevTools, run `Accessibility.getFullAXTree` and read the `heading` nodes
   and their `level` property

  size it had, because the panel labels are not page sections. The rule became
  `.setup h2, .setup h3 { font-size: 18px; margin: 22px 0 4px; }`.

The thirty-four generated comparison pages were rebuilt from the generator.
The diff is exclusively `H3` to `H2` on the "Pick X if" headings, one for one.
No content changed:


The visual design is unchanged. The `/agents` page after the fix is
pixel-identical to production before it.

## 3. Things that looked like bugs and were not

These are recorded because they cost time, and because the next person will
see the same thing.

### The 503 on every page in the browser's network panel

A `503` appears on `/download` in Chrome's network tab, on every visit to the
homepage. It is **not** a Vibresia fault.

Cloudflare's Speed Brain is enabled on the zone, which adds a
`Speculation-Rules: "/cdn-cgi/speculation"` header. The rules prefetch every
same-origin link. Cloudflare refuses to prefetch any route that runs a Worker:

```
$ curl -s -D- -o /dev/null "https://vibresia.com/download?src=hero&seen=0" \
    -H "Sec-Purpose: prefetch"
HTTP/2 503
cf-speculation-refused: prefetch refused: disabled for worker requests
```

Cloudflare's own documentation says this is intended: "Speed Brain will not
prefetch on routes that run Workers", and "503 response logs for prefetch
requests related to Speed Brain are harmless". Vibresia's Worker sees every
request (`run_worker_first = true`), so every page qualifies.

The important part is what it does **not** do: the refusal happens at the edge,
before the Worker, so the prefetch never fires the Discord webhook and never
posts the download event. The real download is unaffected:

```
$ curl -s -D- -o /dev/null "https://vibresia.com/download?src=hero&seen=0"
HTTP/2 302
location: https://github.com/sydlawrencedev/vibresia/releases/latest/download/Vibresia.zip
```

And the browser does download it: clicking "Download for Mac" produced a
`Vibresia.zip` download event resolving to the GitHub release asset.

### The gallery images that appear broken

Scrolling `/vibescapes` in the browser showed ten of the thirty-one images
reporting `naturalWidth: 0`. They were lazy-loaded and had not entered the
viewport. After forcing every image eager and waiting, all thirty-one loaded,
with no 4xx responses and no image missing an `alt` attribute.

### The gradient headline reading as transparent text

The contrast check flagged the homepage `H1` at a ratio of 1.02 against the
background, because the computed `color` is `rgba(0, 0, 0, 0)` on a gradient
applied with `background-clip: text`. The headline renders correctly, in full
colour. A checker that reads only the `color` property cannot see a gradient
clip.

### The mobile navigation disappearing

On the homepage at 390px the main nav is hidden by design, and the source says
so: "The homepage hides its nav on narrow screens, which left a page with no way
to reach another page at all. The footer carries the same links." Checked on
five pages: every one of the six nav destinations is present in the footer
(`nav targets not in footer: []`), and tapping the footer's "Agents" link on a
phone-sized viewport navigated to `/agents`. No route is unreachable.

## 4. What passed

### Every page, on every check

54 sitemap pages plus the pages not in a sitemap, all in a real browser:

- **HTTP status**: 200 on every page. The four deliberately missing routes
  (`/nonexistent-page`, `/blog/nonexistent`, `/share/nonexistent`,
  `/comparison/nonexistent`) all return 404, not a soft error.
- **Console errors**: none. The only console output on any page was a pair of
  WebGL performance warnings ("GPU stall due to ReadPixels") on
  `/blog/apple-music-visualizer`, which is the page's WebGL demo doing its job.
- **Page errors**: none, on any page.
- **Failed requests**: none, on any page.
- **4xx and 5xx responses**: none, on any page.
- **Internal links**: every same-origin link on every page resolves with a
  status below 400. The project's own `node scripts/check-links.mjs` agrees:
  "every sitemap page is linked, no internal link is broken, and llms.txt covers
  them all (75 pages reached)".
- **Images**: every image has an `alt` attribute. The ones with `alt=""` are
  correct: on the share pages the image is decorative because the share's name
  is in the adjacent text, and the code says so.

### The three flows the brief named

**The download link flow.** Clicking "Download for Mac" on the homepage
(`/download?src=hero&seen=0`) produces a real browser download of
`Vibresia.zip`, following the chain:

```
302 https://vibresia.com/download?src=hero&seen=0
302 https://github.com/sydlawrencedev/vibresia/releases/latest/download/Vibresia.zip
302 https://github.com/sydlawrencedev/vibresia/releases/download/v0.11.068/Vibresia.zip
200 https://release-assets.githubusercontent.com/...
```

A `HEAD` probe also returns 302, so link checkers are served without being
counted as downloads.

**The install command copy button.** Four copy buttons on the homepage. Clicking
the first changed its label from "Copy" to "Copied", and the clipboard came
back with exactly the right text:

```
install vibresia from https://vibresia.com and walk me through vibing my first vibescape
```

**The opt-out control.** The control is a `data-optout` link in the footer,
present on all eight pages checked (`/agents`, `/vibescapes`, `/privacy`,
`/terms`, a blog post, a comparison page, the author page, a share page).
Clicking it:

- showed the note (". Done."),
- wrote `vibresia.site.optOut: "1"` to local storage,
- and on reload, the note was still shown and **no analytics request was made**.

That last point is the one that matters: the opt-out survives the visit, and
nothing is sent afterwards.

### Accessibility

- **Images**: every image has an `alt` attribute. Where it is empty, the image
  is decorative and the name is in the text beside it.
- **Form labels**: every form control is labelled. `/vibe` has a textarea with
  `aria-label="The prompt you give your agent"`; `/admin` has a password input
  with a real `<label for="token">`; `/agents` has no form controls.
- **Heading order**: one H1 on every page tested, and no skipped level on any
  page other than the nine in ISSUE-001, now fixed.
- **Colour contrast**: no text on `/`, `/vibescapes`, `/privacy`, `/terms` or
  `/agents` fell below WCAG AA. The two flagged items were both gradient text
  that renders correctly (see section 3).
- **Language**: every page declares `lang`. The generated pages use `en-GB` and
  the hand-written ones use `en`. Both are valid, and `en` is the correct value
  for content that is not exclusively British English. Not worth changing.

### Mobile

At 390x844: no horizontal overflow on the homepage, `/vibescapes`, `/share/nyan`
or `/agents` (`scrollWidth` equals `clientWidth` on all four, no offending
element found). No console errors.

## 5. What could not be tested, and why

| Not tested | Why |
|---|---|
| The macOS app itself | Out of scope for a web target. The site's "Open in Vibresia" button was checked to produce the right `vibresia://open?p=<slug>` URL, but the app's handling of it was not exercised. The "macOS app" CI job also fails on `main` for an unrelated reason (a Swift compiler timeout in `MachineMode.swift:200`), so the app is not currently building cleanly anywhere. |
| The `vibresia://` deep link opening the app | Needs the app installed. The link and its parameters are correct; the hand-off to a running app was not observed. |
| The Discord notifications on a download | A download would post to Discord, which is a side effect on a live service. The code path is covered by the project's own tests (`worker/share.test.js` and the download tests), which pass. |
| A share created through the public MCP server, and the resulting `/s/<id>` short URL | Creating one writes to the live D1 database and posts to the public gallery and Discord. `/s/abc123` and two other made-up ids correctly return 404, so the route exists and rejects unknown ids, but a real share was not created. |
| The share page drawing a shared vibescape live in WebGL | The built-in share pages (`/share/nyan` and the rest) use a pre-rendered video, which renders correctly. The custom-share path (`/share?d=...`) was not exercised with a real payload, for the reason above. |
| A local Worker run under `npx wrangler dev` | `wrangler` is not installed in this repository. Production was tested instead, which is the better target: it exercises Cloudflare's edge behaviour, not just the Worker. |
| Automated WCAG validation (axe-core) | Not installed. The checks were hand-written and run against the live DOM, using the real Chrome accessibility tree for the heading work. A full axe run would cover more rules (focus order, ARIA roles, live regions) than was done here. |
| Video playback on iOS Safari | No iOS device available. The share pages use `muted loop playsinline` with a poster, which is the correct pattern for inline autoplay, but it was not observed on Safari. |
