# Dogfood testing: Vibresia, 2026-11-12

**Target: production, `https://vibresia.com`.** The routine's default
`http://localhost:3000` has nothing listening on it — this repository is a
static site in `site/`, a Cloudflare Worker in `worker/index.js`, and a macOS
app. There is no Next.js dev server. The production site is where a visitor
actually is, and it is the only target that exercises the Worker, Cloudflare's
edge, and the real routes.

**Verdict: three real defects found and fixed, one left as a recommendation.
Zero console errors, zero broken links, zero broken images, zero missing
labels on production.**

## 3. Issues found

### ISSUE-001: The comparisons hub skips a heading level

**Severity: low.** It is a conformance and tooling defect, not a crash and
not a WCAG failure. The reason for the severity is set out honestly in the
evidence below, and it is not the severity yesterday's report gave the same
class of issue.

#### What it is

`https://vibresia.com/comparison` opens `H1` and then goes straight to `H3`:

```
H1 "Vibresia, compared"
H3 "Vibresia vs Magic Music Visuals"
H3 "Vibresia vs Plane9"
H3 "Vibresia vs projectM"
...
H2 "Other apps, side by side"
H3 "Houdini vs TouchDesigner"
```

The second group of entries has an `H2` over it. The first group does not,
so the page starts on a skipped level.

#### Reproduction

1. Open `https://vibresia.com/comparison`
2. Read the heading sequence from the DOM:

```bash
curl -s https://vibresia.com/comparison | grep -oE '<h[1-6][ >]' | head -8
```

```
<h1>
<h3>
<h3>
<h3>
<h3>
<h3>
<h3>
<h2>
```

Or let axe-core judge it:

```
[moderate] heading-order: Heading levels should only increase by one
  -> ["article:nth-child(5) > h3"]
```

#### Evidence, and an honest limit on it

The DOM heading sequence skips `H2`. axe-core flags it. The HTML Living
Standard prohibits skipping heading levels.

**Chrome's computed accessibility tree does not show the skip.** Reading
`Accessibility.getFullAXTree` over CDP, Chrome reparents the orphaned `H3`s
under the later `H2`, so the tree it hands a screen reader reads `H1 → H2 →
H3` with no jump:

```
--- DOM order (main) ---
   H1 Vibresia, compared
   H3 Vibresia vs Magic Music Visuals
   H3 Vibresia vs Plane9
   H3 Vibresia vs projectM

--- AX tree order ---
   H1 "Vibresia, compared"
   H2 "Other apps, side by side"
   H3 "Vibresia vs Magic Music Visuals"
   H3 "Vibresia vs Plane9"
```

So a screen reader user on Chrome does not, on this page, meet a missing
section. The defect is in the document, and it is what an HTML validator,
axe-core, and any assistive technology that reads the DOM rather than
Chrome's computed tree will see. That is why this is **low**, not the
**medium** yesterday's report gave the same class of issue.

#### The fix

`scripts/generate-seo-pages.mjs`, in `renderHub()`: the first group of
entries now has its own section heading, mirroring the one the second group
already had.

```diff
-    const entries = [...ours, ...(referee.length ? ["<h2>Other apps, side by side</h2>...
+    const entries = [
+        ...(ours.length ? ["<h2>Vibresia vs another app</h2>\n    <p>One app against Vibresia, for people deciding whether to make the switch or stick with what they have.</p>", ...ours] : []),
+        ...(referee.length ? ["<h2>Other apps, side by side</h2>...
+    ];
```

#### The tests

Two new tests in `scripts/generate-seo-pages.test.mjs`. The first closes the
coverage gap that let this ship: the heading test now walks the hub as well
as the generated pages.

```diff
+const hub = { page: { slug: "comparison", template: "hub" }, html: renderHub(all.filter(...), records) };
...
-    for (const { page, html } of built) {
+    for (const { page, html } of [...built, hub]) {
```

The second pins the hub's structure.

Both were watched fail before the change:


### ISSUE-002: Every side-by-side table has an empty column header

**Severity: minor.** It is a best-practice rule, not a WCAG failure, and it
does not affect the visual design.

#### What it is

The first column of a comparison table holds the row's label — "Price",
"What it is", "Free version". Its header cell was empty:

```html
<thead><tr><th scope="col"></th><th scope="col">Vibresia</th><th scope="col">TouchDesigner</th></tr></thead>
```

A screen reader reading the header row hears a blank, then an app name, with
nothing saying what the first column holds.

#### Which pages

**45.** Every page with a side-by-side table: the 34 comparison pages, the
12 question pages, and `/blog/best-music-visualizer-for-mac-2026`.

#### Reproduction

1. Open `https://vibresia.com/comparison/vibresia-vs-touchdesigner`
2. axe-core:

```
[minor] empty-table-header: Table header text should not be empty
  -> ["th[scope=\"col\"]:nth-child(1)"]
```

Or read the cell:

```js
document.querySelector('table.versus thead th').outerHTML
// '<th scope="col"></th>'
```

#### The fix

The header now carries a name that only a screen reader sees, so the layout
does not move. Three places in `scripts/generate-seo-pages.mjs`
(`appVerdictHtml`, `versusTableHtml`, `connectionsHtml`), plus one
`.visually-hidden` utility in the generator's stylesheet.

```diff
-    const head = `<th scope="col"></th>${pair.map((s) => ...
+    const head = `<th scope="col"><span class="visually-hidden">What to compare</span></th>${pair.map((s) => ...
```

The connections table says "Connection"; the others say "What to compare".

#### The tests

A new test in `scripts/generate-seo-pages.test.mjs` walks every table header
cell in every generated page and fails on an unnamed one.

**This test was wrong the first time, and the wrongness is worth recording.**
The first version used `/<th([^>]*)>([\s\S]*?)<\/th>/g`, which also matches
`<thead>` — so `<thead>` was read as a `<th>` with the attributes `ead`, the
real header cells were never seen, and the test passed against the
unfixed code. It was only caught because the test was run against the
generator with the fix reverted and it *still* passed. The pattern is now
`/<th(\s[^>]*)>/`, which requires whitespace after `th`:

```js
// <th, not <th: the naive pattern also matches <thead>, and then the
// header cells that follow it are never seen at all.
const cells = [...html.matchAll(/<th(\s[^>]*)>([\s\S]*?)<\/th>/g)];
```

Watched failing on the unfixed generator:

```
✖ every table header cell has a name
  AssertionError [ERR_ASSERTION]: amazon-music-visualizer-mac has a table header cell with no name
```

and passing after.

- `docs/dogfood/2026-11-12-evidence/screenshots/issue-002-before-table-header.png`
- `docs/dogfood/2026-11-12-evidence/screenshots/issue-002-after-table-header.png`

### ISSUE-003: 21 pages have no `<main>` landmark

**Severity: medium.** `region` is the serious half of this: content outside
a landmark is not in the landmarks rotor at all, so a screen reader user
moving by region has no way past the header.

#### What it is

The generated search pages use `<main>`. The hand-written pages and the share
pages use `<div class="wrap">` and nothing else:

```
$ for p in / /vibe /vibescapes /share /privacy; do
    echo -n "$p: "; curl -sS "https://vibresia.com$p" | grep -c '<main'; done
/: 0
/vibe: 0
/vibescapes: 0
/share: 0
/privacy: 1
```

#### Which pages

21: `/`, `/vibe`, `/vibescapes`, `/share`, and the 18 `/share/*` pages.

#### Reproduction

1. Open `https://vibresia.com/`
2. axe-core:

```
[moderate] landmark-one-main: Document should have one main landmark  -> ["html"]
[moderate] region: All page content should be contained by landmarks    -> [".eyebrow","h1",".lede"]
```

The `region` violation on the homepage covers **33 elements**, including the
`h1` and the hero.

#### The fix

`<main>` wraps the content on the four hand-written pages
(`site/index.html`, `site/vibe.html`, `site/vibescapes.html`,
`site/share/index.html`) and in `scripts/generate-share-pages.py`, which
builds the 18 generated share pages.

**The rendering does not change.** None of these pages has a `main` CSS rule
— not in their inline `<style>`, not in `site/chrome.css`,
`site/gallery.css`, `site/legal.css`, `site/vibe.css`, `site/admin.css`,
and not in `site/share/share-page.css`. A bare `<main>` inherits the browser
default `display: block` and changes nothing.

That was verified rather than assumed. A baseline copy of `origin/main` with
freshly regenerated pages and the patched tree were served side by side, and
every element's bounding box, width, height, font-size and colour compared:

```
=== / ===                elements before=320 after=320  added=0 removed=0  IDENTICAL
=== /vibe.html ===       elements before=87  after=87   added=0 removed=0  IDENTICAL
=== /vibescapes.html === elements before=64  after=64   added=0 removed=0  IDENTICAL
=== /share/index.html === elements before=71 after=72  added=1 removed=0  IDENTICAL
=== /share/nyan.html ===  elements before=69 after=70   added=1 removed=0  IDENTICAL
```

The one added element is the `<main>` wrapper itself, with the same box as
the content it now contains.

On `/comparison.html` the comparison is 186 elements before and 188 after,
all 186 matching on identity, width, height, font-size and colour. The two
new elements are the `H2` and its lead-in from `ISSUE-001`.

#### The tests

Two new tests in `scripts/check-marketing.test.mjs`:

- `every page in the site has exactly one main landmark` — walks the ten
  hand-written pages and all 18 share pages.
- `the main landmark wraps the content, not the header or the footer` — the
  `<main>` must open after `</header>` and close before the footer, or the
  banner and the content information end up inside the main landmark.

Watched failing on the unfixed pages:

```

```

and on the unfixed generator:

```

  AssertionError [ERR_ASSERTION]: site/share/badger.html has 0 <main> elements, expected 1
```

and passing after.

### ISSUE-004: The world name on `/vibe` fails WCAG AA contrast

**Severity: medium.** axe rates it `serious`, and it is a WCAG AA failure
rather than a best-practice nit.

#### What it is

The name of the world the agent is drawing — "Liquid gold" — is 11px at
`rgba(167, 159, 196, 0.6)`. Composited against the panel it is
`#69627d` on `#0c0713`, which is **3.45:1**. It needs 4.5:1.

#### Reproduction

1. Open `https://vibresia.com/vibe`
2. axe-core:

```
[serious] color-contrast: Elements must meet minimum color contrast ratio thresholds
  -> ["#world-name"]

  foreground color: #69627d
  background color: #0c0713
  contrastRatio: 3.45
  fontSize: 8.3pt (11px)
  expected contrast ratio: 4.5:1
```

Or read the computed style:

```js
getComputedStyle(document.getElementById('world-name')).color
// "rgba(167, 159, 196, 0.6)"
```

#### The fix

`site/vibe.css`, one line:

```diff
-.panel-label.dim { color: rgba(167, 159, 196, 0.6); }
+.panel-label.dim { color: rgba(167, 159, 196, 0.8); }
```

At 0.8 alpha the colour composites to 5.38:1, and still reads as the
quieter of the two labels. The rule is used by one element on one page.

## 4. Left alone, on purpose

### The gallery card alt text repeats the visible title

**Severity: low.** On `/vibescapes`, each card's image has `alt="Neon Wave"`
and the card's visible title is also "Neon Wave". axe reports
`image-redundant-alt` (best-practice, not WCAG).

It was not fixed, because the fix is not obviously right. The image is the
card's main visual and the alt is its accessible name in every context where
the text is not rendered. Making it `alt=""` would be correct for a
decorative image next to visible text and wrong for an image whose text
label might be hidden by a layout that does not exist yet. One rule on one
page, and no user is blocked by it. It is recorded here rather than fixed.

### The gallery images read as broken on first scroll

Ten of the thirty-one images on `/vibescapes` report `naturalWidth: 0`
before they scroll into view. They are lazy-loaded. After forcing every
image eager and waiting, all thirty-one loaded with no 4xx responses and no
image missing an `alt` attribute.

This was in yesterday's report and is still true. It is not a defect.

## 5. Things that looked like bugs and were not

### The analytics beacon fires when you opt out

Clicking the footer's opt-out link still sends one `POST /ingest/batch/`
if the click lands more than 2.5 seconds after the page loaded. Measured:

```
A: click at 300ms  -> NO POST to /ingest/batch/
B: click at 1500ms -> NO POST to /ingest/batch/
C: click at 4000ms -> POST /ingest/batch/
```

This is not a bug. The pageview is queued on load and flushed 2.5 seconds
later; the opt-out drops the queue, which `site/analytics.js` says it does
and does. Click inside the window and nothing is sent. Click after it and
the pageview describing the visit was already sent, before there was a
click to stop it.

What yesterday's report said — that after opting out and reloading, no
analytics request is made — is still exactly true, and was re-checked:

```
after reload, requests: [ 'GET https://vibresia.com/analytics.js' ]
```

The script is still fetched; it reads the opt-out and returns before it
sends anything.

### Chrome's accessibility tree hides the `/comparison` heading skip

Covered in `ISSUE-001`. It is recorded here as well because it changes how
the evidence should be read: the AX tree shows no jump, so the AX tree
alone would not have found this. The DOM sequence and axe-core did.

### The `501 Unsupported method ('POST')` in the local server's console

`python3 -m http.server` cannot serve the Worker's `/ingest/batch/`. That is
the static test server, not the site. On production the same request
returns 200.

### The `404` for `/api/gallery` in the local server's console

The share pages fetch the gallery from the Worker's API. A static server has
no such route. On production it returns 200.
